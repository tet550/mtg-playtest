# 席分離（明示指定時のみ）

通常は [ai-vs-ai.md](ai-vs-ai.md) を使い、この文書は読まない。

## 席を分けて回す

1つのエージェントが両者を操作すると、**相手の手札を見た判断が必ず混ざる**。
見ないつもりでも、同じ文脈に情報がある以上その影響は取り除けないし、
破ったことがログに残らないので後から確かめようもない。
だから役割を分け、**情報の境界をプロンプトで作る**。

### 事前に確かめること（環境によっては動かない）

- **`mtg-player` が起動できるか。** `.claude/agents/*.md` の `tools:` に、その環境で
  サブエージェントに渡せないツールしか書いていないと「ゼロツール」と判定されて
  起動を拒否される。**ファイルを読めないツールを1つだけ**渡してある
  （現状は `WebSearch`。本文で「使うな」と指示している）。
  それでも拒否されるなら、`general-purpose` に `mtg-player.md` の本文を
  そのままプロンプトとして渡し、「ツールを使うな・`playtest/` 配下を読むな」を
  明示したうえで、返ってきた `tool_uses: 0` で確認する。
- **`SendMessage` が使えるか。** 使えればプレイヤー役の文脈を持ち越せるが、
  無い環境では毎回フルプロンプトを送り直すことになる。そのときは
  **1手ずつではなく1ターン分をまとめて聞く**（メイン→戦闘→第2メインを1回で返させる）。

## 役割

| 役 | 誰 | できること | できないこと |
|---|---|---|---|
| **ジャッジ（進行役）** | 本体セッション | 盤面の書き換え全部・フェイズ進行・スタックの解決・SBA・結果の記録 | プレイヤーの判断を代わりにしない |
| **プレイヤー P1 / P2** | `mtg-player` サブエージェント×2 | 渡された1画面を見て行動を決めて返す | **ファイルもコマンドも触れない** |
| **検証役** | `mtg-rules-verifier` サブエージェント | ルール判定を敵対的に確かめる | 盤面を書き換えない・有利不利は評価しない |

**盤面を書き換えるのはジャッジだけ。** プレイヤーはコマンドを「提案」し、
ジャッジが適法性を確かめてから実行する。こうしないと undo の粒度と
ターン進行の主導権が壊れる。

### なぜプレイヤーにファイルを触らせないのか

`--as P1` で相手の手札を読めなくしても、状態ファイルを直接開けば全部見える。
**サブエージェントにファイルを読む道具を渡さない**のが、隠匿情報を守る確実な方法。
その代わり、判断に要るものはジャッジが `view` で全部渡す。

`.claude/agents/mtg-player.md` の `tools:` は**カンマ区切りの並び**で書く形式なので、
空にはできない（ゼロツールと判定されて起動を拒否される環境がある）。
**ローカルファイルを読めないツールを1つだけ**与えて実質ゼロにしてある
（現状は `WebSearch`。使わないよう本文でも指示している）。
ここに何を書けるかは環境によって変わるので、変えるときは実際に1回起動して確かめること。

**守られたことは事後に確かめられる。** サブエージェントの結果には
`tool_uses: N` が付いてくるので、**プレイヤー役は必ず 0 になっているはず**。
0 でなければその手は疑うこと。0 なら、そのエージェントは状態ファイルを
一度も開いていない。

> **注意**: `.claude/agents/*.md` は**セッションの開始時に読まれる**。
> 追加・変更した直後のセッションでは、`mtg-player` が呼べない
> （`Agent type 'mtg-player' not found`）か、変更前の `tools:` のまま起動を
> 拒否される（`would be spawned with zero tools`）。新しいセッションを始めるまでは、
> `general-purpose` に `mtg-player.md` の本文をそのままプロンプトとして渡し、
> 「ツールを使うな・`playtest/` 配下を読むな」を明示したうえで、
> 返ってきた `tool_uses: 0` で確認する。

## 1手の流れ

```
ジャッジ: python $M --state S --as P1 view P1     # P1に渡す1画面を作る
          ↓ その出力＋「今の状況／決めてほしいこと／方針」をプロンプトにして
Agent(mtg-player) を起動
          ↓ DECISION / COMMANDS / REASON / UNCERTAIN が返る
ジャッジ: COMMANDS の適法性を確かめる
          - マナは足りているか（用途制限を含めて）
          - タイミングは正しいか（ソーサリー限定・優先権を持っているか）
          - 対象は適正か
          UNCERTAIN に何か書いてあれば mtg-rules-verifier を呼ぶ
          ↓ 問題なければ
python $M --state S run <提案されたコマンドを並べたファイル>
          ↓
誘発・SBA・継続的効果をジャッジが処理し、次の優先権へ
```

`view` は**その席のぶんしか出ない**（`--as` の対象なので、他席の `view` は拒否される）。

## 優先権を渡すかどうか

[full-guide.md](full-guide.md) の「優先権を渡すかどうかは、聞く前に数える」をそのまま使う。
AI同士では**飛ばしても誰も文句を言わない**ので、ジャッジが機械的に数えること。

1. 相手の無タップのマナ源（土地以外も）
2. マナの要らない起動型能力（`{T}` だけ・生け贄だけ）
3. 1・2 で払えるマナがあるなら、手札の瞬速・インスタント
4. 遅延誘発のメモ（`effect`）

全部空ならプレイヤーを呼ばずに進める（進めたことは書く）。
1つでもあればプレイヤーを呼ぶ。**「たぶん何も無い」で飛ばさない。**

## 検証役を呼ぶタイミング

- プレイヤーの返答の `UNCERTAIN` が「なし」でないとき
- **無限ループ・複数ターンにまたがるコンボが主張されたとき（必ず）**
- 継続的効果の種類別（レイヤー）、置換効果、コピー可能な値が絡むとき
- 「これで勝ち」という主張が出たとき

検証役には**主張の全文・関係するカードのテキスト・盤面**をプロンプトで渡す。
`VERDICT: 不成立` なら、その手は差し戻してプレイヤーに再考させる。

## 無限コンボの扱い

1. プレイヤーに**1周の収支**を書かせる（何を消費し、何がいくつ増えるか）
2. 検証役に発散するかを確かめさせる
3. 成立するなら、**実行前に回数を宣言**させる。宣言してから記帳する
4. `token ... -n <回数>` と `mod` で最終状態を作り、ループの内容を `note` に残す
5. 選択の余地がないループなら `end --draw`（CR 104.4b）

**「無限」と言われたら記帳する前に必ず検証**すること。
`mtg.py` は記帳係なので、成立していないコンボもそのまま記録してしまう。

## 連戦の回し方

```bash
M=".claude/skills/mtg-playtest/scripts/mtg.py"
# storage-layout.mdに従って実際の開始日・席・未使用番号を選ぶ。以下は例。
D="playtest/20260909-1412-bo1-dw-vs-piza"
S="$D/g01.json"
R="$D/results.jsonl"       # 結果は1つのファイルに寄せる

# 1ゲームごとに状態ファイルを分ける（undo 履歴が混ざらない）
python $M --state $S init --deck1 A --deck2 B --seed <毎回変える> --first P1 --prefetch
...
python $M --state $S --results $R end --winner P1 --reason "..." --tag "A-vs-B"

# 全部終わってから
python $M --state $S --results $R stats --tag "A-vs-B"
```

**`--results` を付け忘れると、結果は状態ファイルの隣に貯まる。** ゲームごとに
ディレクトリを分けていると集計もその数だけ割れるので、`end` と `stats` の
両方に同じパスを渡すこと。

- **seed は毎ゲーム変える**（`python -c "import secrets;print(secrets.randbelow(10**9))"`）。
  結果ファイルに残るので後から同じゲームを再現できる
- **先手は交互に**（`--first P1` / `--first P2`）。実戦では敗者が選ぶが、統計を取るなら
  交互のほうが偏らない。どちらにしたかは `stats` の先手/後手の内訳に出る。
  1戦だけ回して先手も抽選したいときは `--first random`（seed から決まるので再現できる）
- サイド後は登録を増やさず、対局フォルダの `g02-<略称>.txt` を
  `init --deckN <パス> --deckN-name <素の構築の登録名>` で読む（[storage-layout.md](storage-layout.md)）。
  `--tag` を揃えれば1つのマッチとして集計される
- 両者のプレイ方針は**開始時に文章で決めて固定**し、プレイヤー役のプロンプトに毎回同じものを入れる。
  ここがぶれると、ばらつきがデッキ由来かエージェント由来か切り分けられない

## コストを抑える

- **1手ごとに `mtg.py` を呼ばない。** プレイヤーが返した COMMANDS はまとめて `run` に流す
- **1手ごとにプレイヤー役を呼ばない。** 1回5〜6万トークンかかる。
  選択の余地があるまとまり（1ターン分、または戦闘の1区切り）単位で聞く
- 何も起きないステップはプレイヤーを呼ばずに `phase to` / `turn next --to ... --draw` で飛ばす
- 進捗・保存版・終了報告は [log-format.md](log-format.md) に従う。根拠参照も席ごとの可視範囲を守る。
- `view` は長いので、**プレイヤーを呼ぶときだけ**作る。ジャッジ自身は `show` で足りる

## 事後の確認

- `audit.jsonl`（状態ファイルの隣）に、隠匿情報を読もうとした記録が残る。
  席・コマンド・対象・許可されたかが分かるので、**覗いていないことを示せる**
- `log --player P1` / `--player P2` で、それぞれの視点のログを確認できる
- 結果に納得できないときは、`--state` を別名にコピーしてから `undo` で戻して分岐を試す
