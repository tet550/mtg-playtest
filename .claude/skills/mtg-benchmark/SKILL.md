# MTG ベンチマークの実行と採点

ベンチマークは「同じ条件で回して、前と比べる」ための道具なので、**回す側が期待値を見た時点で測定にならない**。
このスキルの本体は手順ではなく、実行フェーズと採点フェーズを分ける**目隠しの規律**にある。

## 対象

`benchmarks/<YYYYMMDD>-<topic>/` のうち、`run/setup.py` と `score.py` を持つもの。現在は
`benchmarks/20260914-jund-vs-piza/`。構成と置き方の規約は [benchmarks/README.md](../../../benchmarks/README.md)。

```text
benchmarks/<topic>/
  run/       実行フェーズが読んでよい（brief.md / games.json / setup.py）
  expected/  採点フェーズまで開かない（cases.json / conditions.json / testcases.md）
  score.py   採点。出力に期待値を含む
  verify.py  A群。出力に期待値（初手）を含む
  decklists/ 実施時点のスナップショット
```

## 目隠しの規律（最優先）

1. **実行フェーズでは `expected/` 配下・`score.py`・`verify.py`・過去の `score.md`・過去のreportを開かない。**
   期待値そのものだけでなく、「何ターンで決まるはず」「どの札を切ってはいけない」といった**合否条件も
   プレイの指針になってしまう**。読んだ状態で回した結果は、基準値との比較に使えない。
2. **このセッションが既に期待値を読んでいる場合**（採点した直後・ユーザーが貼った・前の測定の続きなど）は、
   同じセッションで回さない。実行フェーズを**サブエージェント（`mtg-player` ではなく汎用エージェント1つに
   1ゲーム）**へ渡すか、別セッションで回す。渡すのは実行フォルダのパス・ゲーム名・`run/brief.md` だけで、
   期待値・過去の結果・「こう回すとよい」という助言を渡さない。
3. **ゲーム間で学習しない。** seed 1 の敗因を seed 2 のプレイに反映しない。反映すると5戦が独立でなくなり、
   平均も勝率も意味を失う。サブエージェントに分ける場合は1ゲーム1エージェントにする。
4. 測定条件を変えたいとき（方針文書を足す・規定を変える・思考予算を上げる）は、**回す前に**変更し、
   `setup.py --condition <札>` にその内容を記録する。回しながら条件を変えない。

読んでしまった場合は隠さない。採点の「条件」欄にそのまま書き、参考値として扱う。

## 1. 準備

```bash
python benchmarks/20260914-jund-vs-piza/run/setup.py --condition a
```

実行フォルダ（`playtest/_checks/<日時>-bench-<topic>/`）・`manifest.json`・session短縮名・各ゲームの
`init` コマンドが出る。`--seeds 9141,9143` で絞れる。`--condition` は何を変えて測るかの札で、既定は
`a`（現行のまま）。ネットワークを使いたくないときは `--offline`（キャッシュ完備のときだけ通る）。

出力に期待値は含まれないので、ここまでは実行フェーズと同じセッションで構わない。

## 2. 実行（blind）

読むのは `run/brief.md` と、mtg-playtest の[AI同士の軽量テストプレイ](../mtg-playtest/references/ai-vs-ai.md)。
ベンチマーク固有のプレイ指針は無い。**普段どおり回すことが測定条件そのもの**で、普段と違う手順を踏むと
測っている対象が変わる。

- `setup.py` が出した `init` を1ゲームずつ実行し、決着まで進めてから次のゲームへ。
- 決着は `end --winner <席> --reason <理由> --tag <manifestのtag>`。投了は
  [投了条件](../mtg-playtest/references/concede.md)を満たすときだけ。
- 記録を後から整形しない。`note` の訂正・`undo`・バッチの切り方**そのものが測定対象**（B群）なので、
  見栄えのための事後編集は結果を壊す。

## 3. 採点（blind 解除）

全ゲームの `end` / `concede` が済んでから。

```bash
python benchmarks/20260914-jund-vs-piza/score.py playtest/_checks/<実行フォルダ>
```

`score.md` が実行フォルダに出る。内訳は

- **0. 実行の同一性** … デッキのハッシュ・seed・先手が基準どおりか。ここがNGなら以降の比較は無効。
- **A. 再現性** … `verify.py` を呼び、同じseedの初手が固定されているか。
- **B. プロセス回帰** … 証跡と書かれたバッチから機械的に数える（訂正note・undo・`turn next`の位置・
  attack前の区切り・`--oid`の先走りなど）。
- **C. プレイ品質** … `results.jsonl` の勝者・決着ターン・ライフ・マリガンを基準値と並べる。

**C群のうち、コンボ成立ターンと個別プレイの合否は機械では取れない。** 採点者が証跡
（`output/<game>/turn-starts.md` と `run-*.jsonl`、`note` の E/R）を読んで判断し、実行フォルダに
`observations.json` を書いてから `score.py` を再実行する。条件の本文は `expected/conditions.json` の `play`。

```json
{"9141": {"combo_turn": 12, "checks": {"C6": "OK", "C7": "NG"}, "note": "根拠を1行"}}
```

`OK` / `NG` / `NA`（その席が成立条件に到達しなかった等）を使い、NGには証跡の該当箇所を `note` に書く。

終了コードは 0（すべて期待どおり）／1（同一性・A群・B群のいずれかが不一致）／2（B群までは通りC群だけ未達）。

## 4. 報告

`score.md` を正本にして、実行フォルダの `report.md` へ次だけを足す。

- 条件（`--condition` の内容と、目隠しを破った事実があればそれ）
- 基準値と食い違った項目と、証跡上の原因
- 基準値そのものを更新すべきだと判断した項目（更新は別作業。勝手に `--update` しない）

**期待値の書き換えは測定ではない。** `verify.py --update` や `expected/` の編集は、基準を更新すると
決めたときだけ、差分をレビューできる形で単独の変更として行う。測定結果が合わないから直す、をしない。

## 新しいベンチマークを足すとき

`benchmarks/README.md` の規約に従い、`run/`（目隠し側）と `expected/`（期待値側）を最初から分ける。
期待値・合否条件・過去の実測を `run/` に置かない。`setup.py` と `score.py` は
`benchmarks/20260914-jund-vs-piza/` のものを雛形にする。
