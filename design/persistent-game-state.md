# 紋章・常在型能力・速度・昼夜の設計検討

2026-09-10。現行実装の調査と公式ルール確認に基づく提案。動作コードの変更は含まない。[誘発処理案](trigger-processing.md)・[関連効果案](effect-relations.md)と併せて使う。

方針見直し: 実装範囲は [軽量な管理方針](lightweight-management.md) を優先する。以下は機能追加時の注意点であり、全ルールの自動化を求める要件ではない。状態保存とAIの判断支援を先に行う。

## 結論と現状

「どこに保存するか」と「いつ処理するか」を別に定義する必要がある。紋章を永続バフ、速度をカウンター、昼夜を毎ターンの誘発として代用すると、終了条件やタイミングを誤る。

| 対象 | 現行 | 必要な拡張 |
|---|---|---|
| 紋章 | command領域・紋章専用objectなし。effectメモでしか表現できない | 統率領域の独立object、そこから有効な能力 |
| 常在型能力 | fxで装着先・固定対象・自軍クリーチャーへの基本P/T、加算、キーワードを導出 | 有効領域・条件・種類別・依存関係・ゲーム上の許可/禁止 |
| 速度 | 専用状態・速度増加の誘発なし。pcounterは任意名を保存するだけ | プレイヤー状態、SBAによる開始、発生源のない誘発、回数制限 |
| 昼夜 | 専用状態・詠唱回数集計・変身処理なし | ゲーム共有状態、ターン履歴、アンタップ内処理、現在面 |
| 両面カード | cardcacheにはfaces/layoutがあるが、mtgの特性表示は代表面が中心 | 現在面からの特性・能力の取得、変身時の再計算 |

fxの常在型scopeとuntil=sourceは発生源が戦場にいることを要求する。この条件では紋章や墓地で働く能力を表現できない。新しい有効領域を許可するだけでなく、発生源の生存条件と、能力が機能する条件を分離する。

## 共通のデータモデル

保存場所は次のように分ける。以下は概念上のキーであり、新規CLIではない。

```text
objects: カード、トークン、紋章、スタック上の呪文/能力をkindで区別
zones.command: 統率領域のオブジェクト参照
players[P1].speed: null または速度の値
players[P1].counters: 毒・エネルギー・経験値等
game.designations.day_night: neither / day / night
game.designations.monarch: null / プレイヤー参照
turn_history: ターンID、アクティブ席、各席の詠唱回数等
ability_instances: 有効な常在型・誘発型・起動型能力
trigger_instances: イベントにより発生した個別の誘発
continuous_effects: 種類別・依存関係に従って計算する効果
permissions/restrictions: 呪文・起動・攻撃等への許可と禁止
```

処理の種類は、継続的な評価、イベント確定前の置換/軽減、SBA、ターン起因処理、スタックを使う誘発に分ける。永続しているという理由だけで同じ処理経路へ入れない。

## 紋章

- 紋章は統率領域で機能する独立オブジェクト。kind=emblemを内部識別に使うが、カードタイプのEmblemを持つことにはしない。普通のパーマネントやトークンとして生成しない。
- 所有者・コントローラー・能力定義・作成イベント・表示ラベルを持つ。作成したプレインズウォーカーへの参照は由来の記録であり、有効期限ではない。
- プレインズウォーカーが離れても残す。同じ紋章を複数得たら別IDにし、特に誘発能力を名前でまとめない。
- 常在型能力はcommandを有効領域として評価し、誘発能力は共通のイベント購読に登録する。紋章が新たな能力を与える場合も能力インスタンスとして扱う。
- battlefield限定の除去・全体除去・パーマネント数集計に入れない。通常のmove/tokenコマンドで紋章を戦場や墓地へ送る操作は拒否する。
- 「紋章の数」だけの保存では足りない。誰がどの能力をいくつ持つかを保存し、作成のundoは能力登録もまとめて戻す。

## 常在型能力

常在型能力の定義から、現在有効な効果・能力・制限を導出する。基本フィールドはsource、active_zones、condition、recipient_selector、operations、layer、timestamp、dependencies。

| 種類 | 例 | 判定する場所 |
|---|---|---|
| 特性変更 | 全体+1/+1、基本P/T、種類・色変更 | 表示・戦闘・SBA共通の特性計算 |
| 能力付与・喪失 | 果敢を得る、能力を失う、速度4の間だけ能力を持つ | 有効能力一覧を再計算し、誘発の購読も更新 |
| コントロール変更 | 特定のパーマネントをコントロールする | 所有者と分離したコントロールの導出 |
| 行動の許可・禁止 | 墓地から唱えられる、攻撃できない | 行動の事前検証。文面を表示するだけにしない |
| コスト変更 | 呪文が軽くなる、追加コスト | cast/activateのコスト計算 |
| 置換・軽減 | 墓地へ行く代わりに追放、ダメージ増減 | 元イベントの確定前。誘発検出は確定後の結果を見る |

「新しく登録したものが常に勝つ」では不十分。種類別・細分類、依存関係、タイムスタンプを扱う。未対応の相互作用は確定値と区別し、関連する自動処理を止める。

現行のhas_kwはオラクル文字列に能力があるかも見るため、能力喪失を追加するなら入口を統一する必要がある。oracle、fx、表示、戦闘が別々に能力判定をしない。

動的な常在型効果と、解決時に対象集合が決まる一時効果は別に維持する。最大速度を失う等の状態変化で能力の購読は停止しても、既にスタックへ置かれた誘発や、解決済みの独立した効果を一緒に消さない。

## 速度

速度はプレイヤー固有の値であり、カウンターではない。未開始のnullを保存し、効果が数値を参照するときだけ0として読む。

1. 有効な「エンジン始動！」を持つパーマネントをコントロールし、速度が未開始なら、SBAで1にする。ETB誘発としてスタックに置かない。コントロールを得た場合も判定する。
2. 速度1以上のプレイヤーには、固有の速度増加誘発を登録する。発生源カードは存在しないため、trigger.source_refはnullを許し、rule_idとcontrollerで識別する。
3. 自分のターンの相手のライフ減少イベントから生成し、ターン内に一度だけ誘発したことを**誘発時**に記録する。解決時に記録すると、解決前の追加ライフ減少で重複する。
4. 速度4未満のif条件は誘発時・解決時に確認する。誘発が打ち消されても同じターンの使用済み記録は戻さない。undoなら対応する状態ごと戻す。
5. 始動能力のあるカードが戦場を離れても、既にある速度と固有誘発を消さない。複数の始動カードがあっても固有誘発を重複作成しない。
6. 最大速度の能力は速度4を条件とする常在型能力として評価する。条件を満たしただけで一律に「最大速度になった誘発」を作らない。与えられる能力自身が誘発型なら、そのイベントを待つ。

ライフ減少はダメージだけから拾わない。支払い・直接失う効果・ゲーム効果で低い値へ設定する場合も共通のライフ変更イベントを使う。軽減後にライフが減らなかったダメージ、感染等でライフ減少にならないものを区別する。途中で失ってから回復した場合も、最終差分0だけで見落とさない。

記帳の訂正はゲーム内のライフ変更イベントと区別する。修正のつもりでlife --setを実行し速度が誘発する事態を防ぐ。多人数では「1人以上の対戦相手」をまとめて扱う設計にしておくが、初期実装は現在の2席に限定する。

## 昼夜

昼夜はゲーム全体で共有するneither/day/nightの状態。対応パーマネントがなくなっても、一度始まった状態の追跡を続ける。

- アンタップ・ステップ内の専用処理として、前ターンのアクティブ席がそのターンに唱えた呪文数を確認する。昼で0回なら夜、夜で2回以上なら昼。両席の合計ではない。
- turn nextは「フェイズ・イン/アウト→昼夜判定→通常アンタップ」の順序を持つ必要がある。ここで誘発した能力は保存し、優先権を得る時点までスタック登録を待つ。
- 土地プレイ・起動能力・単に作られた呪文コピーは詠唱数に含めない。実際に唱えた呪文は後で打ち消されても回数を取り消さない。
- 前ターンの記録はturn_idに結び付ける。先手後手交互だけを前提にせず、追加ターンでも直前のターンのアクティブ席を参照する。アンタップが飛ばされたときはそこでの昼夜判定も行わない。
- 効果による昼夜変更も同じ遷移関数を使う。同じ状態を再指定しただけなら変更イベントを作らない。
- 日暮/夜明の対応面を変える際に、oidやincarnationを変えず、タップ・ダメージ・カウンター・装着を維持する。変身をmoveや明滅として記帳しない。
- cardcacheのfacesを参照し、現在面のタイプ・P/T・能力を取得する経路をcard_of等へ統合する。夜に出る場合は適切な面での登場として処理し、表面と裏面の二重ETBを出さない。
- スタック上の表面、戦場での現在面、マナ総量の参照面等は同じ意味ではない。facesを差し替えるだけの実装にせず、特性ごとのルールを保持する。
- 古い狼男の変身条件、通常の変身、日暮/夜明、モードを持つ両面カードをlayout/能力定義で区別する。

既存セーブに詠唱数がなければ「0回」と推測しない。unknownとして再開時に必要な記録を確認する。ログのstack pushを全件castとみなして補完することもしない。

## 同じ仕組みで扱う候補

| 項目 | 保存先・拡張方向 |
|---|---|
| 毒・エネルギー・経験値 | プレイヤーのcounters。増殖等が参照する対象として維持 |
| 統治者・イニシアチブ | ゲーム共有の保持者参照と、規則由来の誘発・状態遷移 |
| 都市の承認 | プレイヤーの指定。戦場のパーマネント消失と切り離す |
| 指輪の誘惑 | プレイヤーの進捗と指輪所持者への世代付き参照を分離 |
| ダンジョン | 現在の進行オブジェクト、選択した部屋、部屋能力の誘発 |
| 英雄譚・クラス | カードのカウンター/レベルと、能力が有効になる条件、章の誘発 |
| 祝祭・紛争・獰猛等 | ターン内イベント履歴や現在の盤面から導出。メカニズム名だけで処理を一律化しない |

各項目の個別ルールと例外は実装対象に選んだ時点で確認する。今回の設計でこれらすべての自動処理を約束するものではない。

## 効率・堅牢性

- 共通のcast/life_change/zone_change/step_beginイベントを果敢・速度・昼夜で共有し、同じ履歴を何度も走査しない。
- 速度変更では速度に依存する能力、昼夜変更では現在面に依存する特性と能力を再評価する。単純な常在型効果も変更した値への依存関係を登録する。
- 初期実装は正しさ優先で全再計算し、後に部分再計算へ最適化する。テストで全再計算と部分再計算の一致を確認する。
- 導出値は正本にしない。紋章・現在面・プレイヤー状態・効果定義を保存し、ロード後にも同じP/T・能力・禁止事項が導けるようにする。
- showは「昼／前ターンP2の詠唱1」「P1速度3／今ターン誘発済み」「P1紋章2個」と要点を出し、詳細で根拠イベントへ辿る。
- 状態更新・誘発生成・常在型能力の再計算・保存を同じ操作単位にし、途中の保存やundoで不整合を作らない。

## 実装順と検証

1. [誘発処理案](trigger-processing.md)の個別能力ID・イベント・優先権境界を先に整える。発生源のない規則由来誘発も扱えるよう修正する。
2. command領域と紋章、常在型効果のactive_zones/conditionを追加する。
3. 速度を追加し、SBAと一般誘発と条件付き能力の連携を検証する。
4. faces/current_faceとターン別詠唱数を整え、昼夜を追加する。
5. 常在型能力の対応範囲を広げる。種類別・依存関係未対応のものは個別裁定に残す。

受入テストは、紋章の作成元除去と同名複数、速度開始前後のライフ減少、速度誘発の解決前の再減少・打ち消し、始動カード全除去、最大速度の有効能力更新、前ターンの両席の詠唱数の混同、追加ターン、アンタップ省略、昼夜パーマネント不在、変身時の装備・修整・世代保持、夜の登場面、保存再開・undoを含める。
