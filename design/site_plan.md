# サイト公開の実装計画

今のシステムは 127.0.0.1・1台の PC を前提にしている（[web_design.md](web_design.md) の「サーバーで動かすときに残っていること」）。
これを対戦サイトとして公開し、デッキを登録して AI か招待した人と対戦し、終わった対局を履歴として見返せるようにするまでの計画。

観戦ビューアは単独の静的サイト（`export` → GitHub Pages）としては出さず、対戦サイトの「履歴」と「観戦」の画面として組み込む。
今の観戦ビューアの再生（時系列・Log・Act / Batch ごとの移動）は、そのまま履歴の再生に使う。

方針は「標準ライブラリだけで動く」を保つこと。保存は `sqlite3`、HTTPS は前段のリバース・プロキシ（Caddy など）に任せ、
ASGI への移行は接続数が問題になってから行う。

## 前提（決定済み）

| 論点 | 決定 | 理由・補足 |
|---|---|---|
| 公開先 | VPS 1台 | SQLite と常駐プロセスがそのまま動く。前に Caddy を置いて HTTPS にし、systemd で常駐させる |
| サーバー | 今の `ThreadingHTTPServer` のまま | 依存を増やさない。接続数が問題になってから ASGI へ移す |
| 保存 | SQLite（`sqlite3`） | 1台なら十分。トランザクションで `.lock` ファイルの排他を置き換えられる |
| 利用者の識別 | アカウントを作らず、「所有者の鍵」を Cookie に持たせる | デッキ・対局・履歴の持ち主が分かれば足りる。Cookie を消した・別の端末で使う場合に備え、鍵を戻す「復元 URL」を出す |
| 初版で遊べる形 | 人間 対 AI と、招待 URL で呼んだ人との対人戦 | 対人戦の仕組みは今もあり、足りないのは招待とテスト。マッチングは後に回す |
| 審判と AI の席 | どの対局でも審判は AI。運営側のキーを使い、1日・利用者ごとに上限を設ける | GUI の席は盤面を直接動かさない作りのため、対人戦でも審判が要る |
| モデルの提供元 | 差し替えられるようにする（OpenAI・Anthropic など） | `llm.py` に提供元の層を足し、設定で選ぶ。役割（審判・AI の席）ごとに別の提供元も選べる |
| 履歴の公開範囲 | 終わった対局は既定で公開し、公開一覧に出す。対局を作るときに非公開を選べる | 対人戦では、招待された側が席に着く前にこの設定を見て同意する |
| 履歴を残す期間 | 無期限 | 対局1件は数百 KB。容量が問題になるまで自動では消さない。利用者は自分の対局を消せる |
| 静的な書き出し（`export`・`docs/`） | 開発用の見本として残すが、公開の経路にはしない | 公開する履歴はサイトの中で見せる |

## 画面構成

| 画面 | 中身 | 作るフェーズ |
|---|---|---|
| トップ | サイトの説明、権利表記、各画面への入口 | 3（骨組み）・7（仕上げ） |
| デッキ | 登録・一覧・編集・削除 | 3 |
| 対局を作る | 自分のデッキ、相手（AI か招待）の選択 | 4 |
| 相手待ち | 招待 URL のコピー、相手の到着を待つ | 4 |
| 対局 | 今の GUI の席（`serve --play` の画面） | 既存（4 で対人戦を確かめる） |
| 履歴 | 自分の対局の一覧（進行中・終了）、再生 | 6 |
| 公開の対局 | 終わった公開対局の一覧、再生 | 6 |
| 観戦・共有 | 共有 URL で開く、再生専用の画面（非公開の対局・進行中の対局） | 6 |

画面の行き来は1つのページの中の切り替えにし、今の ES modules の作り（ビルド不要）を保つ。

## フェーズ 1: 保存先を差し替えられるようにする（済み）

- 共通の処理（apply・undo・redo・replay・fork・policy）を `store.BaseStore` に置き、保存先ごとの読み書きだけを実装が持つ
  - `store.GameStore`: 対局フォルダ（今までどおり。CLI・手元の対局の既定）
  - `sqlstore.SqliteGameStore`: SQLite。表は `games`（初期状態・現在状態・cursor・要約・日時）・`log`（1件1行）・`docs`
  - `expect` が合わないときの 409 の決まりは変えていない。排他は SQLite では `BEGIN IMMEDIATE`（DB 全体で書き手1人、読み手は WAL で止まらない）
- 席の鍵と席ごとの非公開設定（止める場所）は「卓の外の文書」（`read_doc` / `write_doc`）にし、SQLite では `docs` の表に入る
- AI のプロンプトと返答は作業ファイルのまま（DB の隣の `<名前>-files/<対局>/prompts/`）
- 対局の要約（`summary`）: 作った日時・更新した日時・終わった日時（巻き戻せば消える）・ターン・各 Player の状態（結果）。
  一覧はこれを使い、更新の新しい順に並ぶ。参加者と所有者の鍵の対応はフェーズ 2 で足す
- 設定: `--db`（か環境変数 `MTGTABLE_DB`）で DB の場所。キーは今までどおり `OPENAI_API_KEY`。`db-import` で対局フォルダを DB へ移す
- 確認: テストを丸ごと両方の保存先で回す（`MTGTABLE_TEST_STORE=sqlite`。CI も両方）。SQLite だけのテストは `tests/test_sqlstore.py`
  （移行・要約・ロールバック・同時の書き込みで1人だけ通ること・CLI の `--db`）

## フェーズ 2: 利用者の識別と鍵（済み）

公開のサーバーは `serve --site`（`--db` が要る。`--play` を含む）。手元の `serve` / `serve --play` は今までどおり。

- 所有者の鍵: 初めて来たブラウザ（`/api/config`）に発行し、Cookie（HttpOnly・SameSite=Lax、127.0.0.1 / localhost 以外では
  Secure）で渡す。DB にはハッシュだけ。1人の所有者が端末ごとに複数の鍵を持てる（`owners.py`、表 `owners`・`owner_keys`）
- 席を取る: 招待の URL を開いたページが、席の鍵で `POST /api/games/<対局>/claim` を呼び、その席をこの所有者のものにする
  （表 `participants`）。以後はその所有者だけが Cookie で入れ、同じ鍵を他の人が使っても通らない（招待の URL が漏れても守られる）
- 復元 URL: ヘッダーの「復元 URL」で作る（`/#recover=...`）。開いた端末に同じ所有者の鍵を足す。何度でも使えて、作り直すと前の URL は無効
- 席の鍵の期限と失効: `invite --ttl 時間`（既定 7日、0 で期限なし）、`revoke`（席は人間の席のまま、作り直すまで誰も使えない）。
  対局が終わった後の書き込みは、もともと席の書き込みの決まり（`_playing`）で断っている。終わった対局の読み取りはフェーズ 6 で決める
- 一覧と読み取り: 自分が席を持つ対局だけを一覧に出し（`my_seat` 付き）、judge の席・鍵の無い対局・他の人の席・
  更新の通知（SSE）も、席を持たない人には見せない
- 書き込み（席の操作・復元・席を取る）は `Origin` がこのサイトのものだけ受ける
- 確認: `tests/test_site.py`（Cookie・席を取る・取った席を他の人が使えない・自分の対局だけ・復元・Origin・期限と失効）。
  ブラウザでも、招待の URL を開いた端末・復元 URL で戻した端末が対局でき、漏れた招待の URL を開いた端末は断られることを確かめた
- 残り: レート制限（所有者の鍵を作れる数を含む）はフェーズ 7

## フェーズ 3: デッキ登録とサイトの骨組み（済み）

- サイトの骨組み（`web/site.js`）: ヘッダーの「トップ・デッキ・対局」で画面を切り替える（URL は `#/top`・`#/decks`・`#/games`）。
  対局が無ければトップから。トップは入口（デッキの登録・招待の URL・復元 URL の説明）だけ。トップとデッキの画面では、
  盤面にしか効かないヘッダーの部品を隠す
- API（`serve --site` のときだけ。どれも自分のデッキだけ・書き込みは Origin を確かめる）:
  `GET /api/decks`（一覧）・`GET /api/decks/<id>`・`POST /api/decks`（登録）・`PUT /api/decks/<id>`・`DELETE /api/decks/<id>`・
  `POST /api/decks/check`（検査だけ。保存しない）。検査に通らなければ 400 と、行ごとの理由（`check.errors`）
- 検査（`decks.check`。登録・更新のたびに行い、通ったものだけを保存する）
  - 書式は `parse_decklist` と同じ読み方で、読めない行・枚数のおかしい行を行番号つきで返す
  - カード名: `carddb.resolve_names` が Scryfall の `/cards/collection` で 75 枚ずつまとめて引く（キャッシュにあれば引かない。
    フォーマットの情報 `legalities` の無い古いキャッシュは引き直す）。分割カード「Fire // Ice」は最初の面で引いて照らし合わせる
    （collection は両方の名前では引けない。本物の API で確かめた）。75 枚のデッキで初回 約 2 秒
  - 構築: メイン 60 枚以上・サイドボード 15 枚まで・同じ名前はメインとサイドを合わせて 4 枚まで（基本土地・「好きな枚数を
    入れてよい」カードは除き、「7 枚まで」などはその数）
  - フォーマット（standard・pioneer・modern・legacy・vintage・pauper・historic・timeless・free）: 禁止・使えないカードは
    行番号つきで断る。制限カード（restricted）は 1 枚まで。free は見ない。使えるか分からないカードは注意（warnings）だけ
  - 入力の制限: 20000 文字・250 行・デッキ名（半角英小文字・数字・ハイフン、40 文字まで、所有者ごとに重ならない）・
    プレイ方針 8000 文字・1人 50 個まで
- 保存: 表 `decks`（所有者・名前・フォーマット・本文・プレイ方針・書いた名前から正式な名前への対応）。`decks.decklist` が
  本文から正式な名前の Decklist を作る（フェーズ 4 で対局を作るとき）
- 画面（`web/decks.js`）: 一覧（編集・削除）と、貼り付け → 「検査する」→「登録する」。理由は行番号つきで出す
- AI のプレイ方針: 対局の初期状態の `meta.decks.<席>.strategy` があれば、それだけをプロンプトに入れる（同じ名前の
  `decklists/strategy/` のファイルは別のデッキのものなので入れない）。フェーズ 4 で、対局を作るときにここへ写す
- 確認: `tests/test_decks.py`（検査の各規則・偽の Scryfall でのまとめ引き・API の権限・プレイ方針）、`web.test.mjs`
  （検査の結果の表示・画面の切り替え）。ブラウザで、トップ → デッキ → 理由つきで断られる → 直して登録 → 編集 → 削除、
  スマホの幅で横にはみ出さないことを確かめた
- フェーズ 4 への申し送り: 両面カードは正式な名前が「Delver of Secrets // Insectile Aberration」になる。リポジトリの
  デッキリストは表の面の名前で書いているので、対局を作るときにどちらで卓に置くか決める

## フェーズ 4: 対局を作る（人間 対 AI・対人戦）

### 4-a 今の対人戦を確かめる（済み）

- p1・p2 の両方に `invite` で鍵を作り、審判だけを AI にして通しで流すテストを足した（`tests/test_pvp.py`）
  - キープ → ターンの受け渡し → 相手のターンの割り込み（止める場所）→ 審判の質問 → 止まった計画の戻り → ブロック → 投了
  - 審判のプロンプトだけが作られ、Player のプロンプトは作られないこと。鍵は自分の席だけで、相手の手札は見えないこと
- 見つかった穴: 依頼（`seat_request`）は、待たれていない席からも出せた。相手が AI なら AI は自分の番にしか書かないので
  表に出なかったが、人間どうしでは、相手が考えている間・審判の質問に答えている間に依頼を送れてしまい、
  審判が順番を飛ばして処理する。ゲームが始まった後は、待たれている席だけが依頼を出せるようにした（ゲーム前の申し出と、
  発言・投了は今までどおり）。GUI も、相手の番の間は「審判に依頼」を押せない（下書きは作っておける）
- それ以外の `autopass`・`waiting_on`・`blocks_undecided`・プロンプトの書き出しの合図は、両方が人間でもそのまま動いた

### 4-b 対局を作る API と画面（済み）

- `POST /api/games`（`lobby.Lobby.create`）: 自分のデッキを選び、相手を選ぶ
  - AI: すぐに対局を作る。自分は p1（席を持つ）、p2 は鍵の無い席（AI）。AI のデッキは `decklists/*.txt`（プレイ方針は
    `decklists/strategy/` のファイル）か自分の登録デッキ（登録したプレイ方針）
  - 人間: 招待（表 `invites`）を作り、URL（`/#/join/<招待>/<鍵>`）を返す
- デッキは作る時点の写しを初期状態の `meta.decks.<席>` に入れる（名前・フォーマット・本文・プレイ方針）。後でデッキを
  編集・削除しても、対局と Replay は変わらない
- 人間の席は席の鍵を作らず、所有者に結び付ける（`participants`。Cookie で入る）。卓の文書 "seats" には鍵の無い人間の席として
  印を置く（AI の席として扱われないように）
- 公開・非公開（既定は公開）を選ぶ。対局の文書 "site" に置く（公開の一覧はフェーズ 6）
- 画面「対局を作る」（`web/lobby.js`）: デッキ・相手・AI のデッキ・公開を選んで作る。AI ならそのまま対局の画面へ
- 両面カードは、書いた名前がそのカードの名前なら（表の面など）その名前で卓に置く（リポジトリのデッキリストと同じ）

### 4-c 招待と待合せ（済み）

- 招待の URL は1回だけ使える（`UPDATE ... WHERE game IS NULL` で先に使用済みにし、同時に着いても対局になるのは1人。
  4人同時に着くテストで確かめた）。期限は 3 日。作った人は URL の作り直し（前の URL は無効、期限も延びる）と取り消しができる
- 招待された人は、相手のデッキの名前・フォーマット・公開かを見て（デッキリストは見せない）、自分の登録デッキを選んで
  席に着く。席に着いたことを公開への同意とする。その時点で対局を作る（招待した人が p1、着いた人が p2。先攻はコイントス）
- 相手待ちの画面: 「対局を作る」の下の招待の一覧。相手待ちの間は 4 秒ごとに見に行き、着いたら「開く」が出る
- 両方そろうと、対局はゲーム前（先攻のキープ待ち）から始まる。審判が動くのは、今は `auto --watch` を動かしたとき（フェーズ 5）

### 4-d 対人戦の運用（済み）

- 投了ボタンは前からある（席の操作の「投了」）
- 接続が切れたとき: 所有者の鍵（Cookie）で同じ席に戻れる（フェーズ 2）。別の端末は復元 URL
- 時間切れ: 人間どうしの対局で、相手（人間）の番のまま 5 分たつと画面に出し、30 分たつと待っている側が
  「時間切れで勝ちにする」を押せる（`POST /api/games/<対局>/timeout`。相手の投了として卓に書く）。自分の番・審判の番・
  AI の番では申し立てられない。時系列（timeline）に `idle`（書き込みが止まってからの秒数・人間の席）を付け、画面が分を数える

### 確認

- `tests/test_pvp.py`（4-a）
- `tests/test_lobby.py`: AI との対局（AI の席・デッキの写し・プレイ方針・公開）、招待（1回だけ・自分の招待には着けない・
  4人同時に着いても1人・期限・作り直し・取り消し）、時間切れ（早すぎる・自分の番・AI の番は断る）
- `web.test.mjs`: 時間切れの知らせ・招待の URL と画面の切り替え
- ブラウザで2人の流れを確かめた: A がデッキを登録 → 招待を作る → B が URL を開いてデッキを選んで席に着く（p2 で対局中）→
  A の一覧が「対局になった」に変わり「開く」で p1 として対局 → 使用済みの URL を開いた3人目は断られる。AI との対局も作れる

## フェーズ 5: AI をサーバーの中で回す（済み）

- 提供元の層（`llm.py`）: openai（Chat Completions。標準ライブラリの urllib のまま）と anthropic（公式の SDK。選んだときだけ
  読み込む。`pip install anthropic`）。設定 `secrets/llm.json`（無ければ前の `openai.json`）か環境変数で、提供元・モデル・
  考える深さ（effort）を選ぶ。審判と AI の席で別々にもできる
  - プロンプトの固定部分の区切り（system[0]・system[1]）は今のまま。anthropic ではそこに `cache_control`（TTL 1時間）を付ける
  - anthropic: `output_config.effort`、断り（`refusal`）はサーバー側の代わりのモデル（`fallbacks: "default"`。受けるモデルだけ）、
    それでも断られたら分類つきの LLMError。既定のモデルは `claude-opus-5-5`
  - 使用量（`usage.jsonl`・`ai_log.jsonl`）は提供元によらず同じ形（`input_tokens`（キャッシュ分を含む）・`output_tokens`・
    `cached_tokens`・`cache_write_tokens`・`total_tokens`・元の `raw`）
- ワーカー（`worker.py`）: `serve --ai`（`--play` と）・`serve --site`（既定。`--no-ai` で止める）で動く。起動時にキーと SDK を
  確かめ、足りなければ止まる
  - 変わった対局（stamp が前と違う）ごとに `llm.run`（自動パス → 審判か AI の席の番なら呼ぶ → 人間の番まで）。
    同じ対局は同時に1つ、全体で 4 対局まで。サーバー自身の書き込みで `Viewer.notify` が起こし、1手ごとに画面へ通知する。
    別のプロセスの書き込みは 2 秒ごとに見る
  - 印（stamp）を取ってからまだ仕事があるかを見直すので、回し終えた直後の人間の書き込みを取りこぼさない
  - ワーカーが動いている間は、席の操作のたびに審判のプロンプトを先に書き出す処理（`auto_build`）をしない（2度作らない）
- 利用の上限（`worker.Limits`。環境変数で変える）: 対局ごとの呼び出し回数（600）とトークン数（600万）、所有者（対局を
  作った人。p1 の持ち主）ごとの1日のトークン数（1000万）、サイト全体の1日のトークン数（1億）。数えた分は DB の表
  `ai_usage`（対局・日・所有者・回数・トークン数）。呼ぶ前に確かめ、超えていれば対局を中断にする
- 中断と再開: 返答を続けて卓に書けない（`llm.run` の決まり。AI の席は一度審判に回してから）・API を呼べない・上限に
  当たったら、卓の文書 "ai" に理由を書いて中断。時系列（timeline）に `ai` を付け、画面に理由と「再開する」を出す。
  再開は席を持つ人だけ（`POST /api/games/<対局>/resume`）
- 確認: `tests/test_llm.py`（提供元・モデル・effort の選び方、anthropic の本文（キャッシュの区切り・fallbacks）、偽の Messages API
  に公式の SDK で送って審判と AI の席が回ること、断りの扱い、使用量の形）、`tests/test_worker.py`（人間が書いたらすぐ回る・
  人間の番の間は呼ばない・上限で中断・鍵の無い再開は断る・再開で続きが回る・API を呼べないと中断・所有者と1日の数え方）。
  ブラウザで、サイトで AI との対局を作り、キープを押すと AI の席のキープと審判のゲーム開始がサーバーの中で回って T1 になる
  ことを確かめた（偽の OpenAI の API）
- 残り: SSE を席ごとの event にすること（今は {version, cursor} を流し、画面が取り直す）

## フェーズ 6: 履歴・公開対局・観戦

今の観戦ビューア（`web.py` の `timeline`・`log`、`web/app.js` の再生）を、権限つきの履歴の画面にする。

- 履歴の一覧: 自分が参加した対局（進行中・終了）。日付・デッキ・相手・結果・ターン数を出し、デッキと結果で絞り込める
- 公開の対局の一覧: 終わった公開対局。新しい順に出し、デッキ名で絞り込める
- 再生: 対局を開くと、今のビューアと同じ形で最初から再生できる（Act / Batch ごと、自動再生、Log）
- 見える範囲
  - 対局中: 参加者は自分の席の視点だけ（今の PlayerView）
  - 終了後の公開対局: 誰でも、どちらかの席の視点か全体（judge）の視点で再生できる
  - 終了後の非公開対局: 参加者だけが、自分の席の視点と全体の視点で再生できる
  - 審判と AI のやりとり（プロンプトと返答の記録）は、公開対局でも参加者にだけ見せる
  - 共有 URL: 非公開の対局や進行中の対局を見せるため、参加者が発行・失効できる再生専用の URL。見せる視点を発行時に選ぶ。
    対局中の共有 URL では全体の視点を出さない。非公開の対人戦で全体の視点を出すには、両方の参加者の同意が要る
- 進行中の観戦: 共有 URL を開いた人には、進行中の対局も遅れずに届く（フェーズ 5 の通知を使う）
- 対局の削除: 参加者が自分の履歴から消せる。対人戦では、両方が消すまで対局の記録は残し、公開一覧からは消した時点で外す
- 性能: 履歴は何度も開かれるので、要求ごとに最初から再生し直す今の作りを改め、終わった対局の時系列は作った結果を保存しておく
- カードの画像と文: サーバーのキャッシュから配る今の形を続ける（ブラウザから Scryfall に直接取りに行く静的版の形は使わない）
- 確認: 自分の履歴に他人の対局が出ないこと、公開一覧に非公開・進行中の対局が出ないこと、終了前に全体の視点が見えないこと、
  失効した共有 URL が拒否されること、共有 URL で書き込めないこと

## フェーズ 7: 悪用への備えと運用、公開

- レート制限: 送り元の IP ごとと、所有者の鍵ごと。招待 URL・共有 URL を作れる数の上限も設ける
- セキュリティ・ヘッダー（CSP など）
- アクセス・ログ、エラーの記録、SQLite の定期バックアップ（履歴は無期限なので、ディスク使用量の監視も入れる）
- VPS での動かし方: Caddy の設定例（HTTPS の自動更新）、systemd のユニット、起動・更新・バックアップの手順
- トップの仕上げ: サイトの説明、`meta description`・OGP・favicon
- 権利表記: Fan Content Policy が求める文言と、Scryfall から取得していることを全画面のフッターに出す
- 利用規約とプライバシー・ポリシー。AI（選んだ提供元）に盤面を送ること、終わった対局が既定で公開されること、
  対人戦の相手と共有 URL で見える情報、履歴を無期限に残すことと消し方も書く。
  あわせて Scryfall の規約と Fan Content Policy に合っているか確認する（サーバーがキャッシュからカードの文と画像を配るため）
- 外向きのアドレス（`--host`）で受けるのは、このフェーズが終わってからにする
