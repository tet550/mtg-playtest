# サイト公開の実装計画

今のシステムは 127.0.0.1・1台の PC を前提にしている（[web_design.md](web_design.md) の「サーバーで動かすときに残っていること」）。
これを対戦サイトとして公開し、デッキを登録して AI か招待した人と対戦し、終わった対局を履歴として見返せるようにするまでの計画。

観戦ビューアは単独の静的サイト（`export` → GitHub Pages）としては出さず、対戦サイトの「履歴」と「観戦」の画面として組み込む。
今の観戦ビューアの再生（時系列・Log・Act / Batch ごとの移動）は、そのまま履歴の再生に使う。

方針は「標準ライブラリだけで動く」を保つこと。保存は `sqlite3`、HTTPS は前段のリバース・プロキシ（Caddy など）に任せ、
ASGI への移行は接続数が問題になってから行う。

## 前提（決定済み）

| 論点 | 決定 | 理由・補足 |
|---|---|---|
| 公開先 | VPS 1台 | SQLite と常駐プロセスがそのまま動く。前に Caddy を置いて HTTPS にし、systemd で常駐させる |
| サーバー | 今の `ThreadingHTTPServer` のまま | 依存を増やさない。接続数が問題になってから ASGI へ移す |
| 保存 | SQLite（`sqlite3`） | 1台なら十分。トランザクションで `.lock` ファイルの排他を置き換えられる |
| 利用者の識別 | アカウントを作らず、「所有者の鍵」を Cookie に持たせる | デッキ・対局・履歴の持ち主が分かれば足りる。Cookie を消した・別の端末で使う場合に備え、鍵を戻す「復元 URL」を出す |
| 初版で遊べる形 | 人間 対 AI と、招待 URL で呼んだ人との対人戦 | 対人戦の仕組みは今もあり、足りないのは招待とテスト。マッチングは後に回す |
| 審判と AI の席 | どの対局でも審判は AI。運営側のキーを使い、1日・利用者ごとに上限を設ける | GUI の席は盤面を直接動かさない作りのため、対人戦でも審判が要る |
| モデルの提供元 | 差し替えられるようにする（OpenAI・Anthropic など） | `llm.py` に提供元の層を足し、設定で選ぶ。役割（審判・AI の席）ごとに別の提供元も選べる |
| 履歴の公開範囲 | 終わった対局は既定で公開し、公開一覧に出す。対局を作るときに非公開を選べる | 対人戦では、招待された側が席に着く前にこの設定を見て同意する |
| 履歴を残す期間 | 無期限 | 対局1件は数百 KB。容量が問題になるまで自動では消さない。利用者は自分の対局を消せる |
| 静的な書き出し（`export`・`docs/`） | 開発用の見本として残すが、公開の経路にはしない | 公開する履歴はサイトの中で見せる |

## 画面構成

| 画面 | 中身 | 作るフェーズ |
|---|---|---|
| トップ | サイトの説明、権利表記、各画面への入口 | 3（骨組み）・7（仕上げ） |
| デッキ | 登録・一覧・編集・削除 | 3 |
| 対局を作る | 自分のデッキ、相手（AI か招待）の選択 | 4 |
| 相手待ち | 招待 URL のコピー、相手の到着を待つ | 4 |
| 対局 | 今の GUI の席（`serve --play` の画面） | 既存（4 で対人戦を確かめる） |
| 履歴 | 自分の対局の一覧（進行中・終了）、再生 | 6 |
| 公開の対局 | 終わった公開対局の一覧、再生 | 6 |
| 観戦・共有 | 共有 URL で開く、再生専用の画面（非公開の対局・進行中の対局） | 6 |

画面の行き来は1つのページの中の切り替えにし、今の ES modules の作り（ビルド不要）を保つ。

## フェーズ 1: 保存先を差し替えられるようにする

- `GameStore`（`mtgtable/store.py`）を「インターフェース」と「ファイルでの実装」に分け、`SqliteGameStore` を足す
  - `apply`・`undo`・`redo`・`cursor`・`read_log`・`lock`・`fork` と、`expect` が合わないときの 409 の決まりは変えない
- 席の鍵と、席ごとの非公開設定（stops）も同じ DB に移す
- 対局に、履歴で使う情報を持たせる: 作った日時・終わった日時・参加者（所有者の鍵との対応）・結果
- サーバーの設定を作る: データの置き場所と、キーを環境変数から読む方法
- 確認: 今の `test_store.py`・`test_play.py` を両方の実装で回す

## フェーズ 2: 利用者の識別と鍵

- 「所有者の鍵」を HttpOnly・Secure・SameSite=Lax の Cookie で発行する。DB にはハッシュだけを保存する
- 復元 URL: 所有者の鍵を別の端末・消えた Cookie に戻すための URL を出す。作り直すと前の URL は無効になる
- 席の鍵に有効期限と失効を足す。対局が終わったら書き込みの鍵は失効させる（読み取りは履歴の権限で判断する）
- 今の `/api/games` は root の下の全対局を返し、鍵を作っていない対局は誰でも読める（`Viewer.games`・`Viewer.guarded`）。
  これを「自分が参加した対局だけ」「権限のない対局は読めない」に変える
- 書き込みの API では、`Origin` ヘッダーを確かめて CSRF を防ぐ
- 確認: 鍵がない・期限切れ・失効済み・別の人の鍵、のそれぞれで拒否されること。他人の対局が一覧に出ないこと

## フェーズ 3: デッキ登録とサイトの骨組み

- サイトの骨組み: トップと画面の切り替え（上の「画面構成」）。この時点ではトップは入口だけ
- API（新しく `mtgtable/decks.py` を作る）
  - `POST /api/decks`（登録）と、一覧・1件の取得・`PUT`・`DELETE`。操作できるのは所有者だけ
  - 読み込みは `parse_decklist` をそのまま使う
- 検査
  - カード名: Scryfall の `/cards/collection` で75枚をまとめて照会し、どの行の、どの名前が見つからなかったかを返す
    （今の `carddb.fetch` は1枚ずつ間隔をあけて問い合わせるので、75枚だと数十秒かかる）
  - 構築ルール: メイン60枚以上、サイドボード15枚以下、同名カードは4枚まで（基本土地は除く）、
    フォーマットで使えるか（`legalities`）
  - 入力の制限: デッキ名の形式（半角英小文字・数字・ハイフン）・文字数・行数・1人が登録できる件数
- 画面（新しく `mtgtable/web/decks.js` を作る）: 貼り付け、エラーの表示、一覧、編集、削除
- AI のプレイ方針は任意の欄にする。書かれていればプロンプトの system[1] に入れ、空なら方針なしで回す
- 確認: 検査の単体テスト（Scryfall はモックにする）と、API の権限テスト

## フェーズ 4: 対局を作る（人間 対 AI・対人戦）

### 4-a 今の対人戦を確かめる

フェーズ 1 より前にやってもよい。

- p1・p2 の両方に `invite` で鍵を作り、審判だけを AI にして、通しで流すテストを足す
  - 依頼を送る → 審判の質問が相手の席に行く → 相手のターンに割り込む → ブロック → 決着、までの流れ
  - 今のテストは、どれも p1 だけに鍵を作る形
- 片方の席が人間である前提に寄っている所があれば直す（`autopass`・`waiting_on`・プロンプトの書き出しの合図など）

### 4-b 対局を作る API と画面

- `POST /api/games`: 自分のデッキを選び、相手の種類を選ぶ
  - AI: 相手のデッキを選ぶ（自分のデッキか、`decklists/` の公開デッキ）。相手の席には鍵を作らない
  - 人間（招待）: 相手の席は空けておき、招待用の URL を返す
- 公開・非公開を選ぶ（既定は公開。終わった後に公開一覧に出る）
- 作る時点でデッキの写しを対局に保存する。後でデッキを編集・削除しても、対局と履歴の再生が壊れないようにするため
- 自分の席の鍵は自動で発行する（今 CLI の `invite` でしている処理）

### 4-c 招待と待合せ（対人戦）

- 招待 URL は1回だけ使える。使われるとその人の席の鍵が発行され、招待 URL は無効になる。期限も付ける
- 招待された側は、公開・非公開の設定を見て、自分の登録デッキを選んでから席に着く（席に着くことを公開への同意とする）。相手が着くまで、対局は「相手待ち」にしておく
- 相手待ちの画面: 作った側は相手が来るのを待ち、URL をコピーできる
- 両方そろったら、審判がゲーム前の処理（マリガン）を始める

### 4-d 対人戦の運用

- 投了ボタン（今の `concede` を GUI から使えるようにする）
- 接続が切れたとき: 鍵があれば同じ URL で戻れる。今もそうなっているかを確かめる
- 放置への対応: 決めた時間、自分の番で操作がなければ相手に知らせる。さらに長ければ、相手が勝ちを申し立てられるようにする

### 確認

- 4-a の対人戦の通しテスト
- 対局作成から T1 までのテスト（AI 戦と対人戦の両方）
- 招待 URL の権限テスト: 使い回し、期限切れ、すでに埋まった席

## フェーズ 5: AI をサーバーの中で回す

- 提供元の層: `llm.py` の OpenAI 専用の部分（`complete`・`request_body`・使用量の記録）を、提供元ごとの実装に分ける
  - まず OpenAI（今の実装）と Anthropic を用意する。設定で提供元とモデルを選び、審判・AI の席で別々にもできる
  - プロンプトの固定部分の区切り（system[0]・system[1]）は今のまま。Anthropic ではそこにキャッシュの指定（TTL 1時間）を付ける
  - 使用量の記録（`usage.jsonl`）は、提供元によらず同じ形（入力・出力・キャッシュのトークン数）にそろえる
- `serve` の中に AI 用のワーカーを置き、審判か AI の席が待たれたら `llm.step` を呼ぶ。
  今は `auto --watch` を別のプロセスで動かしている所を置き換える。対人戦では審判だけを回す
- 盤面が変わったら、書いた側がワーカーと SSE に知らせる（今の SSE は 0.5 秒ごとに更新時刻を見ている）。
  対人戦では相手の操作が、観戦では進行がすぐ届くことに直結する
- 利用料を守る仕組み
  - 対局ごと・利用者ごと・1日ごとに、呼び出し回数とトークン数の上限を設ける
  - 上限を超えたら対局を止めて、画面にそのことを出す
- 失敗したときは、決めた回数だけやり直し、それでも駄目なら対局を「中断」にする
- 確認: API をモックにして、ワーカー経由で対局が進むこと（AI 戦と対人戦の両方、提供元ごと）

## フェーズ 6: 履歴・公開対局・観戦

今の観戦ビューア（`web.py` の `timeline`・`log`、`web/app.js` の再生）を、権限つきの履歴の画面にする。

- 履歴の一覧: 自分が参加した対局（進行中・終了）。日付・デッキ・相手・結果・ターン数を出し、デッキと結果で絞り込める
- 公開の対局の一覧: 終わった公開対局。新しい順に出し、デッキ名で絞り込める
- 再生: 対局を開くと、今のビューアと同じ形で最初から再生できる（Act / Batch ごと、自動再生、Log）
- 見える範囲
  - 対局中: 参加者は自分の席の視点だけ（今の PlayerView）
  - 終了後の公開対局: 誰でも、どちらかの席の視点か全体（judge）の視点で再生できる
  - 終了後の非公開対局: 参加者だけが、自分の席の視点と全体の視点で再生できる
  - 審判と AI のやりとり（プロンプトと返答の記録）は、公開対局でも参加者にだけ見せる
  - 共有 URL: 非公開の対局や進行中の対局を見せるため、参加者が発行・失効できる再生専用の URL。見せる視点を発行時に選ぶ。
    対局中の共有 URL では全体の視点を出さない。非公開の対人戦で全体の視点を出すには、両方の参加者の同意が要る
- 進行中の観戦: 共有 URL を開いた人には、進行中の対局も遅れずに届く（フェーズ 5 の通知を使う）
- 対局の削除: 参加者が自分の履歴から消せる。対人戦では、両方が消すまで対局の記録は残し、公開一覧からは消した時点で外す
- 性能: 履歴は何度も開かれるので、要求ごとに最初から再生し直す今の作りを改め、終わった対局の時系列は作った結果を保存しておく
- カードの画像と文: サーバーのキャッシュから配る今の形を続ける（ブラウザから Scryfall に直接取りに行く静的版の形は使わない）
- 確認: 自分の履歴に他人の対局が出ないこと、公開一覧に非公開・進行中の対局が出ないこと、終了前に全体の視点が見えないこと、
  失効した共有 URL が拒否されること、共有 URL で書き込めないこと

## フェーズ 7: 悪用への備えと運用、公開

- レート制限: 送り元の IP ごとと、所有者の鍵ごと。招待 URL・共有 URL を作れる数の上限も設ける
- セキュリティ・ヘッダー（CSP など）
- アクセス・ログ、エラーの記録、SQLite の定期バックアップ（履歴は無期限なので、ディスク使用量の監視も入れる）
- VPS での動かし方: Caddy の設定例（HTTPS の自動更新）、systemd のユニット、起動・更新・バックアップの手順
- トップの仕上げ: サイトの説明、`meta description`・OGP・favicon
- 権利表記: Fan Content Policy が求める文言と、Scryfall から取得していることを全画面のフッターに出す
- 利用規約とプライバシー・ポリシー。AI（選んだ提供元）に盤面を送ること、終わった対局が既定で公開されること、
  対人戦の相手と共有 URL で見える情報、履歴を無期限に残すことと消し方も書く。
  あわせて Scryfall の規約と Fan Content Policy に合っているか確認する（サーバーがキャッシュからカードの文と画像を配るため）
- 外向きのアドレス（`--host`）で受けるのは、このフェーズが終わってからにする

## 初版の後に回すもの

- マッチング（知らない人と自動で組む）とロビー
- アカウント（OAuth）と、デッキごとの対戦成績
- 審判なしで、人間どうしが卓を直接動かす対局
- ASGI への移行と、静的ファイルの CDN 配信
- AI にデッキの方針を下書きさせる機能
