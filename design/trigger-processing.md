# 果敢・上陸などの誘発処理: 調査と改善案

2026-09-09時点のコードを確認し、合成盤面で問題を再現した検討資料。以下の現行実装・不具合は調査当時の記録。本資料は操作早見表ではない。

2026-09-10追記: 今後の実装範囲は [軽量な管理方針](lightweight-management.md) を優先する。本資料の全面的なイベント・自動誘発基盤は一括実装せず、再現済みの不具合修正と処理待ち管理から進める。

改修済み: 能力オブジェクトの独立化、上陸候補の自己名による誤除外と複数行の欠落を修正。AI宣言式のpending台帳・解決区間・確認メモ・明示詠唱記録を追加した。現在の操作は [bookkeeping.md](../.claude/skills/mtg-playtest/references/bookkeeping.md)。以下の自動検出案全体を実装したものではない。

## 結論

優先度は「能力オブジェクトの独立化と候補欠落の修正」→「永続的なイベント・誘発待ち管理」→「果敢の定型処理」→「確認済みカード別の上陸」→「他の誘発への拡張」。既存のfxは解決後の継続効果に使い、誘発自体の管理は別の台帳にする。linkedの帰還誘発も共通台帳へ接続する。

## 現行実装

| 対象 | 現在の処理 | 注意点 |
|---|---|---|
| 果敢・唱えるたび | 専用の検出処理なし。AIがstack push、修整、stack popを記帳 | grant/fxに「果敢」と書いても、キーワードの表示・保持だけで誘発しない |
| 上陸・他のパーマネントが出るたび | mtg.pyのenter_watchersが戦場のオラクルを走査し、report_enter_watchersが候補を表示 | 候補の永続化、確定、未処理チェック、解決は行わない |
| 自身のETB | 候補抽出で意図的に除外 | 出たカードの確認をAIに委ねる |
| 死亡・攻撃・ドロー・ライフ獲得等 | 一般的な検出・処理待ち機構なし | AIによる手動記帳 |
| linkedの帰還誘発 | waiting→pending→stack→returned/counteredを保存 | 一般の誘発とは別管理 |
| stack上の一般能力 | 名前キーで共有するcards定義、個々のoid、note、任意のsource_ref/ability_key | 効果を実行する定義、イベントとの関連、解決済みフラグはない |

上陸の候補表示の呼び出し元はmove、search、token、関連帰還、linked playの土地。共通のmove_many自体から発行しているわけではなく、呼び出し元に依存する。tokenは複数体を生成した後、各oidについて繰り返し走査する。

前回の70件のテスト成功は、これら一般誘発の自動処理を保証しない。既存の誘発候補テストはクリーチャー限定・複合タイプ等の一部に限られる。

## 今回再現した問題

1. **効果文に自身の名前がある上陸が候補から落ちる。** 合成カードScoutに `Landfall — Whenever a land you control enters, Scout gets +1/+1 until end of turn.` を持たせたところ候補0件。自己ETB除外が条件部と効果部を区別せず、行内の自身のカード名で全体を捨てるため。
2. **1枚の異なる誘発がまとめて1件になる。** 上陸でライフ獲得する行とドローする行を別々に持たせたところ候補1件。最初の一致でbreakしているため。候補表示としても後続の能力を見落とす。
3. **同名能力の種類情報を共有している。** Prowessという名前の能力を2個スタックに置き、1個popすると、もう1個が残っていてもcards[Prowess]が削除された。能力が通常カードとして検索される原因になる。名前は表示専用にし、種類・内容は各能力オブジェクトに保存する必要がある。

コードから分かる追加の弱点:

- 「you control」等の判定も行全体にかかり、効果側の文章を誘発条件と誤認する余地がある。
- 候補は警告だけなので、見逃しても一般誘発の未処理としてフェイズ進行・解決を止められない。
- 呪文を唱えたこととスタックへの単なる移動・コピーを表すイベントが分離されていない。stack pushをすべて唱えた扱いにすると果敢が過剰誘発する。
- tokenや複数帰還で「1体ごと」と「1体以上が同時に」を区別するイベント境界がない。
- 離脱前情報は世代付き参照・source_history・一部のlast_known_sourceにあるが、同時イベント全体の効果適用済み盤面を固定していない。死亡誘発を広げる前に補強が必要。

## 推奨する処理構造

### イベント、誘発待ち、解決後の効果を分離する

1. 操作とそのコスト・選択・置換処理を確認し、イベントを確定する。
2. 確定イベントと、該当する時点の能力定義から誘発インスタンスを保存する。発生しただけでは修整等を適用しない。
3. 現在の呪文・能力の解決を終え、適切な時点でSBAを安定するまで適用する。
4. 次に優先権を渡す前に、対象・モード・必要な選択と誘発順を確定してスタックへ置く。
5. 応答後、最上段の1件を解決する。果敢ならfxの固定対象・eot修整を作り、同じ保存単位でその誘発を解決済みにする。

解決途中にドロー等の新しい誘発が生じても、その場で別の呪文を唱えられるようにしない。処理待ちがあることを理由に、途中の解決手順やSBAまで禁止することも避ける。「解決中」と「優先権を渡せる境界」を状態として区別する。

### イベントの型と識別

- spell_cast: 唱え終わった呪文の世代、唱えた席、スタック上の特性、コスト支払い完了を保存する。copy_to_stackや単なるmoveとは別イベント。
- zone_change: 共通移動処理から発行する。複数同時移動のevent_idと、個々のoccurrence_idを分ける。トークン生成も同じenterイベントの供給元へ接続する。
- combat、draw、life_gain、counter_change、step_begin等は段階的に追加する。
- データはイベント直前・直後の必要な特性、能力、コントローラーを保持する。離脱を見る能力は直前、通常のETBは新規登場したものも含む直後の状態を使う。ルール上の例外は定義で指定する。
- 同じコマンドの再表示・検出再実行は同じイベントを再処理するだけとし、重複登録しない。undo後はイベント台帳・処理済み位置も一緒に戻す。

### 誘発台帳

```text
trigger_id
event_id / occurrence_id
source_ref = oid + incarnation
ability_instance_id / definition_version
controller_at_trigger
condition / intervening_if
targets / modes / choices
status = needs_review | pending | stacked | resolving | resolved | countered | dismissed
stack_object_id / resolution_effect_ids / evidence
```

同じ表示名でも別インスタンスにする。重複排除キーはevent・発生源世代・能力インスタンス・発生回・追加誘発番号。複数の果敢を1つに潰さず、同じ能力をoracleのキーワード欄と注釈文から二重登録もしない。

不確かな候補はneeds_reviewに保存する。「誘発しない」と判断する場合は短い理由を残し、全候補を再読させない。一般誘発のpendingとlinked帰還のpendingは、同じ優先権境界で確認する。linkedの即時帰還は誘発台帳へ変換しない。

## 果敢から自動化する

果敢は条件と効果が定型なので、検証済みプリセットに適する。

- spell_castのスタック上の特性が非クリーチャーで、唱えた席が果敢のコントローラーと一致する場合に生成する。アーティファクト・クリーチャーは非該当。
- 土地プレイ、戦場に出すだけ、呪文コピーを直接スタックへ置くことは該当させない。コピーを「唱える」指示の場合は別。
- 元の呪文が後で打ち消されても、既に生成した誘発は残る。果敢自身の打ち消しは別に扱う。
- 解決時に発生源の元の世代へ+1/+1・eotを登録する。明滅して戻った同じoidへは付け直さない。果敢そのものを後で失っても、既に生成した誘発を消さない。
- fx/grantから与えられた果敢も、能力インスタンスとして検出対象にする。単なるhas_kwの真偽値では複数個を数えられない。

通常は唱える操作の出力に「果敢 T31/T32: 2件、スタック登録待ち」と短く出す。既知・対象なし・順序が結果に影響しないものは登録操作をまとめられる。ただし各誘発はスタック上に個別に残し、一括で+2/+2に置き換えない。

## 上陸は条件の共通化と、カード別の効果定義

上陸という語だけで効果を決めない。土地が出たイベントを共通に使い、カードごとに確認した本文を能力定義へ登録する。

- 土地プレイ、サーチ、リアニメイト、帰還、土地トークンから同じ検出経路を通す。
- 戦場にあるものが土地に変わっただけ、コントロールが変わっただけではenterイベントを出さない。
- 「1つ出るたび」は個別occurrence、「1つ以上」は同時イベント単位で数える。
- 対象・任意処理・条件・ドロー・トークン生成を効果定義で区別する。未知のドロー結果や選択を跨いでバッチを進めない。
- 誘発回数の追加・抑止、ターン内回数制限、if節、反射誘発は明示的な定義またはneeds_reviewにする。テキストの「if」を一律に二度判定しない。

## 効率化

- 能力定義はカード/有効な能力の変更時に一度作り、cast・enter・death等のイベント種別と席で索引を持つ。各イベントで戦場全カードの全文を読み直さない。
- 同時移動後の有効特性を一度計算して共有し、入ったカード数ぶんオラクル走査を繰り返さない。初期実装は安全側に索引を再構築し、最適化は計測後に行う。
- 更新条件には装着、付与、能力喪失、コントロール変更、明滅を含める。未対応の能力変更時に古い索引を使わない。
- 画面は新規候補・未処理件数・解決結果だけ。詳細はtrigger_idからイベントとカード定義へ辿る。
- 誘発解決、fx作成、スタック除去、証跡を一操作で確定する。保存再開や再実行で同じ解決を二度適用しない。
- loop等の省略記帳はイベントを飛ばす経路になり得る。誘発を含む反復が検証済みの場合だけ回数付きイベントにまとめ、不明な選択・乱数・盤面変化がある場合は通常進行へ戻す。
- 速度改善は未計測。イベント当たりの候補走査数・カード情報参照数、100体同時登場での時間、CLI呼び出し回数、出力行数を測り、正確さと併せて比較する。

## 導入手順と受入テスト

1. 先に今回の3件の再現を回帰テスト化し、自己参照判定・複数能力表示・同名能力の個別データを修正する。
2. 共通イベント、誘発台帳、解決境界を実装し、linkedの帰還誘発を接続。最初は検出後の選択をAIに残す。
3. 明示的なcast操作と果敢プリセットを追加。旧stack pushは唱えたか不明なため、履歴から推測しない。
4. 実際に使うカードの上陸定義を登録し、他のETB・死亡・攻撃等を追加する。
5. CLI・早見表・詳細ガイドを同じ変更で更新する。提案構文を実装済みの早見表に混ぜない。

必須の振る舞いテスト:

- 自身の名前を効果文に含む上陸、同一カードの複数能力、同名能力が複数スタックにある状態。
- 非クリーチャー呪文、アーティファクト・クリーチャー、土地、コピー、コピーを唱える、唱えずに出す、唱えた呪文の打ち消し。
- 果敢が複数、装備からの果敢、誘発後の能力喪失・明滅、複数ターンのeot終了。
- 複数土地同時登場、同時に登場する能力の発生源、土地トークン、土地化・コントロール変更。
- 両席の同時誘発と順序、対象選択、対象不適正化、if節の再確認、任意処理、追加誘発・抑止・回数制限。
- 発生源と他のクリーチャーの同時死亡、解決途中のドロー誘発、誘発を契機とする誘発。
- 確定・却下・スタック登録・解決の各段階で保存/再開/undo。解決の再実行は効果を重複させない。
