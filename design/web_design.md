# 観戦ビューアの設計

読み取り専用の Table Engine ビューア（人間が席を持って操作する GUI の対局は、後半の「GUI の対局」）。ゲームの正本は対局フォルダ、公開範囲の判定は
Python の `info.player_view` に置き、ブラウザは受け取った view の再生と描画を担当する。

## 見直した点

従来の `app.js` は通信、差分復元、描画、画面操作を同時に扱っていた。
配信方式の分岐が描画にも入り、通信中に席・対局が変わると古い結果を反映できた。
責務の境界を作り、変更時に確認する範囲を小さくする。

| ファイル | 責務 |
|---|---|
| `web.py` | PlayerView・時系列・Log の生成、HTTP/SSE 配信、静的書き出し |
| `web/source.js` | ローカル API と静的 JSON の違い、画像・オラクル、更新購読、古い要求結果の破棄 |
| `web/timeline.js` | キーフレームと差分から指定位置の view を復元。DOM・通信に依存しない |
| `web/render.js` | カード、盤面、戦闘、スタック、Log の DOM 描画 |
| `web/motion.js` | カードの動き（タップ・移動・束への出し入れ）。描画の前後の位置を比べ、重ねた層で写しを動かす |
| `web/app.js` | 選択状態、読み込み結果の反映、再生、ユーザー操作、初期化、席の鍵の受け取り |
| `web/play.js` | GUI の対局の操作（メニュー・Act の組み立て・送信・操作パネル）。後半を参照 |
| `web/dom.js` | DOM 要素の生成と ID 検索 |

データは `source → app → Timeline → render` と流れる。
描画からの Log 移動はコールバックで app に戻す。循環 import は作らない。
画面上の状態は app が作成して renderer に渡し、カード名索引や攻撃表示などの派生値は
renderer が view から更新する。汎用的な状態管理ライブラリは導入しない。

## 読み込みと再生

- 対局と席を要求開始時に固定し、時系列と Log をまとめて読み込む。Log の取得は judge のみ。
- 新しい要求が始まったら、それより古い要求の成功・失敗は画面に反映しない。
- 対局・席の変更時は再生を停止し、古い盤面・詳細・Log を消して購読を張り直す。
- カード詳細も、後から選んだカードや変更後の view を古いオラクル応答で上書きしない。
- 再生中の移動では通信せず、Timeline のキャッシュから復元する。
- カードの動きは 1 件ずつの移動・自動再生・Live の小さな更新だけ（`ui.animate`）。スライダーや Log での移動、
  一度に多くのカードが動く描画では動かさない。view に無いカードは動かさないので、非公開の情報は漏れない。
- キーフレーム間隔と差分形式は既存のまま。ルートの置換は古いキーを残さず置き換える。

HTTP の時系列と Log は別リクエストのままなので、CLI の書き込みと完全に同一時点の
スナップショットを保証するものではない。更新は既存の SSE により再取得する。
厳密な整合性が必要になった場合はサーバー側で一つのスナップショットとして返す。

## 維持した構成と判断

ビルド不要の ES modules と Python 標準ライブラリを維持する。小規模な読み取り専用画面に
フレームワーク、バンドラー、汎用イベントバスは追加しない。
Python 側は既に Viewer・Handler・export_site に役割が分かれているため、今回さらに分割しない。
CSS とレイアウトは維持し、描画の部分更新は性能上の必要性が判明した時点で検討する。

`mtgtable/web/` がソースの正本、`docs/static/` は公開用コピー。
export は JS/CSS をまとめてコピーするため、モジュール追加のたびにコピー対象を列挙し直す必要はない。
既存の公開データを変えずにフロントだけ更新する場合も、JS/CSS を一式同期する。

## 検証

`python -m unittest discover -s tests` で API、席ごとの公開範囲、静的書き出しを検証する。
`node --test tests/web.test.mjs`（Node.js 24）で差分復元、キャッシュ、要求の競合、配信方式、
購読の終了を検証する。Node.js はテスト用であり、利用者が観戦するためには不要。

# GUI の対局（Human vs AI。`serve --play`）

観戦ビューアをそのまま土台にし、人間の席だけ「操作できる観戦」にする。ルールの判定は今までどおりしない。
席（人間・AI）は卓に op を書かず、審判への依頼・回答と、盤面を変えない宣言だけを書く（request_play_design。
初めは人間もブラウザから Batch を直接書いていたが、隠れた情報をいつでも引けたため置き換えた）。

## 構成

```
ブラウザ（人間 p1）──POST request/declare/answer──▶ web.py ─┐
        ▲                                         ├─ GameStore（.lock・expect）── 対局フォルダ
        └──────── SSE（version/cursor）◀──────────┘          ▲
AI（p2・Claude Code）── CLI apply ／ wait ───────────────────┘
```

| 部品 | 責務 |
|---|---|
| `store.py` | 書き込みの排他。`.lock`（O_EXCL のロック・ファイル。別プロセスの CLI とサーバーの間でも効く）と `expect`（見ていた cursor と違えば `StaleCursor`）。log も一時ファイルからの置き換えで書く |
| `play.py` | 席の鍵（`invite`。`seats.json` には SHA-256 だけ）、待たれている Player（`waiting_on`）、`wait`、Player に見せる log |
| `web.py` | `--play` のときだけ `POST /api/games/<g>/request`・`declare`・`answer`（`play.seat_batch` が宣言に変える）。鍵で守る対局（`seats.json` がある対局）は読むのも鍵の席だけ |
| `web/play.js` | カード・束・Player・スタックのメニュー、下書き（依頼の行）の組み立て、送信、操作パネル。`render.js` には hooks（クリックの受け口と描画後の呼び出し）と `ui.marks`（選んだ対象・下書きの印）・`ui.planned`（引く予定の「？」）だけを足した |
| `web/source.js` | 席の鍵を、その対局・席の要求にだけ `Authorization: Bearer` で付ける。POST の 409 は `error.stale` |

## 決めたこと

- **手番の受け渡しは優先権で表す。** `waiting_on` は 優先権 → （全員パスなら）スタックの一番上のコントローラー →
  クリンナップなら次のターンの Player → アクティブ・プレイヤー の順。画面の「あなたの番」と AI の `wait` が同じ定義を使う。
  ai_play_and_log_design 7章の「優先権の受け渡し」の最初の形。自動パス・タイムアウトは状態にまだ持たせない
  （GUI の「唱えた後に優先権を渡す」はブラウザ側の設定）
- **AI は `wait` で待つ。** 人間が1件ずつ書いても返らず、待たれているのが自分になる・相手の宣言・決着・巻き戻しで返る。
  見るのは「自分が最後に書いた件」より後なので、`apply` と `wait` の間に人間が書いても取りこぼさない。
  AI の会話を常駐させず、Claude Code の1コマンドとして待てる（既定 540 秒。Bash の上限 10 分の内側）
- **席の鍵。** 席を名乗るだけでは書けない（ローカルでも、ブラウザのタブから相手の席・judge を開けない）。鍵は URL の
  `#key=`（フラグメントなのでサーバーのログ・Referer に出ない）で渡し、ページが localStorage に移してアドレス・バーから消す。
  席としての書き込みは、Batch の actor をサーバーが席に固定し、Act ごとの `actor`・`proxy` を拒む
- **楽観的排他。** GUI は表示中の cursor を `expect` に付ける。AI が先に書いていたら 409 で断り、最新を読み直させる。
  見ていない盤面に対する操作を通さない（例: AI が除去した後のクリーチャーで攻撃する）
- **（置き換え済み）席の取り消しは自分の直前の Act だけ。** 今は席が卓に書かないので、下書きの行を送る前に外すだけ（request_play_design）。 相手の後に書いた Act は戻せない（409）。ライブラリーから引く・見る・探す・
  シャッフルした Act も戻せない（403。知ったままやり直せるため。ai_play_and_log_design 7章の「巻き戻しと乱数」）。
  それ以外の巻き戻しは宣言で相手（AI）に頼み、AI が `undo --to N` する（会話での運用と同じ）
- **（置き換え済み）人間の操作は即時の Act が基本。** 今は下書きの行（request_play_design）。 タップ・移動・ライフなどは1クリック＝1 Act。唱える・起動は対象と支払いを選んでから
  1つの Act（`cast` / `stack_push`＋`pay`）。解決・攻撃・ブロックは下書きに集めて確定で1つの Act
  （解決は最後に `stack_remove`、ブロックが無ければ `declare no_block`）
- **Player の席の Log** は、今の CLI の対局で AI が報告に出している範囲（ラベルと op の要約。event は出さない）。
  見る人ごとの対局の記録（ai_play_and_log_design 6.2）ができたら置き換える
- 観戦（`--play` なし、または鍵の無い対局）の動きは変えない。静的書き出し（`export`）は `config.play` が偽なので操作 UI は出ない

## サーバーで動かすときに残っていること

ローカル（127.0.0.1・1台の PC）を前提に作り、置き換える境目を次の所に寄せた。公開までの計画は [site_plan.md](site_plan.md)。

| 項目 | 今 | サーバーでは |
|---|---|---|
| 正本の保存 | 対局フォルダ（JSON・JSONL。`store.GameStore`）か SQLite（`sqlstore.SqliteGameStore`、`--db`）。共通の処理は `BaseStore` | 済み（SQLite）。台数を増やすなら同じ形で PostgreSQL などを足す |
| 排他 | `.lock` ファイル（対局フォルダ）か `BEGIN IMMEDIATE`（SQLite。DB 全体で書き手1人） | 済み。`expect` はそのまま（409 の約束事は API に残す） |
| 更新の通知 | SSE が 0.5 秒ごとに mtime を見る | 書いた側が通知を出す（ai_play_and_log_design 6.4 の act_begin / act_end）。席ごとに公開範囲で絞った event を流す |
| AI の接続 | `auto`（OpenAI の API）か、プロンプトを書き出して人がモデルに渡す（下の「AI の席のプロンプト」） | `auto` の回し方をサーバーのワーカーに移す（審判か AI の席が待たれたら呼ぶ）。審判（judge）の API は別の鍵 |
| 認証 | 席ごとの鍵（ベアラー・トークン）。HTTP のまま | HTTPS 必須。鍵の有効期限・失効、対局の作成・招待の API。`--host` で外に出すのはそれまで行わない |
| 時系列 | 要求ごとに最初から Replay（小さな対局なら十分） | キーフレームのキャッシュを保存し、差分だけ足す |
| 多重の接続 | `ThreadingHTTPServer` | ASGI などへ。静的ファイルは CDN |

## 検証

# AI の席のプロンプト（`prompt` / `answer`。API 化の前段）

AI の席を「プロンプトを送って Batch を返してもらう」形にする。自動のときは API（今は OpenAI）に送るだけに
なるよう、今の段階からプロンプトを API の本文（`request.json`）の形で作り、手動では同じ中身を貼る。

## 1回の判断 = 1通

- 毎回のメッセージは1通で、前のやりとりを積まない。続きの計画は返答の `memo` で持ち越し、次のプロンプトに入れる
- ツール（`view` / `oracle` / `apply` を AI が呼ぶ形）は使わない。判断に要るものを先に全部入れる:
  前回の自分の書き込みより後の log（ラベルと op の要約）、memo、自分の席の view（カード名付き。ライブラリーの既知・墓地も）、
  自分のデッキに無い・知っているカードのオラクル、前回の失敗の理由
- Batch は「次に判断が要る所まで」。ドローなどで区切ったら、まだ自分の番なので `answer` がすぐ次のプロンプトを作る

ツールで回す形（AI が自分で `oracle` を引き、失敗をその場で直す）は、自動化のときに足せる。1通の形を先にしたのは、
手動で回せること、往復が少ないこと、固定部分が大きくキャッシュの効果が大きいこと、のため。

## キャッシュ

| 位置 | 中身 | 変わるとき |
|---|---|---|
| system[0]（区切り） | `prompts/player.md`・cli.md の「id と名前」以降・patterns.md・rules.md | これらのファイルを直したとき。全対局・全席で共有 |
| system[1]（区切り） | 席・デッキ名・自分のデッキのオラクル一覧（サイドボードなし）・`decklists/strategy/<デッキ名>*.md` | 対局ごと（初期状態から作るので、対局中は変わらない） |
| messages[0] | 今回の状況 | 毎回 |

- 固定部分には cursor・version・時刻・ライフなど、対局の進行で変わる値を入れない（テストで確かめている）
- 区切りの TTL は1時間。人間の相手は1手に5分以上かけることがあり、5分の TTL では毎回書き直しになる
- 固定部分の順番は「共通 → 席」。共通の部分は別の対局・別の席とも共有できる
- `system-1.md` / `system-2.md` は中身が変わったときだけ書き直す（差分が出たら、キャッシュが外れたということ）

## 返答の約束と適用

- 返答の最後の JSON のコード・ブロック `{"batch": {...} | null, "memo": "..."}` を読む。前の文は考えとして `NNNN.response.md` に残る
- 適用は `GameStore.apply(..., expect=プロンプトを作ったときの cursor)`。返答を待つ間に相手が書いていたら適用せず、
  最新の盤面でプロンプトを作り直す。他の Player の `actor` は拒む（`proxy` は選択の余地が無い進行にだけ使う約束）
- 失敗（JSON が無い・Act の失敗）は理由を付けてプロンプトを作り直す。失敗した Act より前の Act は残る（Batch の仕様どおり）

## 自動化で足すもの

- ワーカー: `waiting_on` が AI の席になったら `build` → `client.messages.create(**request.json)` → `apply_answer`
- 拒否（`stop_reason: "refusal"`）とフォールバック、失敗の再試行の上限、1手あたりの費用の記録（`usage` のキャッシュ読み取り量）
- 返答の形を構造化出力（`output_config.format`）で固めるか。Batch の op は種類が多いので、まずはコード・ブロックの約束で運用する

# Player と審判の分離（2段目。人間も AI も審判を通す）

GUI のボタンで MTG の全部の操作を用意するのは現実的でない。そこで「何をするかを決める役（Player）」と
「卓を動かしルールを見る役（審判）」を分ける（basic_design 4章・27節）。

```
Player（人間 GUI / AI）── intent（意図の文）──▶ 審判 ── Batch（各 Act に actor）──▶ 卓
          ▲                                       │
          └──────────── ask（質問・選択肢）◀───────┘   answer（回答）は審判へ
```

## 卓の記録

審判とのやりとりは宣言（`declare`）として卓に残す。Undo・Replay・観戦がそのまま効く。

| kind | 書く人 | player | 意味 |
|---|---|---|---|
| `intent` | Player | 本人 | 審判への依頼（やりたいこと） |
| `ask` | 審判 | 質問される Player | 質問。`choices` に選択肢（無ければ自由記述） |
| `answer` | Player | 本人 | 質問への回答 |
| `ruled` | 審判 | 依頼した Player | ここまでの依頼・回答を処理した印と、両者に見せる説明 |

- `play.waiting_on`: 最後の `ruled` より後に `intent` / `answer` があれば **審判**。回答の無い `ask` があれば、その Player。
  それ以外は今までどおり（ゲーム前のキープ・優先権・スタック・クリンナップ）
- ゲーム開始: キープ・マリガンの宣言は審判を通さないが、全員がキープしたら一度だけ審判の番になる（`game_start_pending`。
  最後のキープより後の `ruled` で終わる）。審判はマリガンで下に置くカードを本人に聞き、開始時の手札から使うカード
  （<Leyline> 類）を先攻から順に処理し、先攻の T1 を始める
- 審判の Batch は judge の Batch で、各 Act に `actor`（操作する Player）を付ける。`proxy` は使わない。最後に `ruled`、続けて `ask`
- GUI の席から `ruled` / `ask` は書けない（サーバーが断る）。人間の GUI の直接の操作（タップ・唱えるなど）は今までどおり書ける

## 役割ごとのプロンプト

| 役割 | system[0]（全対局で同じ） | system[1]（対局の間は同じ） | 毎回 | 返す形 |
|---|---|---|---|---|
| Player（intent） | `player_intent.md` + rules.md | 席・自分のデッキ・戦略メモ | 前回からの出来事・memo・自分の view・相手のカード・自分への質問 | `{"action", "text", "memo"}` |
| 審判 | `judge.md` + cli.md・patterns.md・rules.md | 両者のデッキ | 処理する依頼（回答なら元の質問も）・最近 40 件の記録・全情報の盤面 | `{"batch", "ask", "message"}` |
| Player（direct） | `player.md` + 審判と同じリファレンス | 席・自分のデッキ・戦略メモ | Player と同じ | `{"batch", "memo"}` |

- Player には操作の書式を渡さない（判断だけ）。プロンプトが小さくなり、書式の誤りは審判1か所に集まる
- 審判は全情報を見るが、label・message・質問は両者に見えるので、非公開の情報を書かない約束にしている（judge.md）
- 簡単な action（pass / keep / mulligan / no_block / concede）は審判を通さずに、その席の操作として書く（往復を減らす）
- 質問されている間、その Player の action は `answer`（と `concede`）だけを受け付ける

## 手動の回し方と自動化

`next --ai p2` が審判か AI の席の番まで待ってプロンプトを書き、`answer` が最後のプロンプトの役割として返答を書く
（`prompts/pending.json`）。自動では `auto`（`llm.py`）が `next_role` → `build` → OpenAI の Chat Completions → `apply_response` を回す。
`request.json` は Chat Completions の本文（system 2つ ＋ user）。OpenAI のプロンプト・キャッシュは先頭が同じなら自動で効くので、
キャッシュの区切りは書かない。キーは `secrets/openai_api_key`（git 管理外）か `OPENAI_API_KEY`。

残り: 審判の誤りの扱い（Player が異議を出す宣言と、審判の巻き戻し）、審判の memo（長い対局での経緯）、
人間の GUI の直接の操作を審判が後から確かめるか、同じ局面で intent と direct を比べる検証（fork）。

## 人間の行動は先に記録し、審判がまとめて確かめる（置き換え済み）

**この節は前の形。** 今は席が卓に何も書かず、下書きを依頼として送り、審判が卓に書く（request_play_design）。
未確認の行動・席の取り消し・`visible_cursor` は外した。

1手ごとに審判（LLM）を呼ぶと、待ち時間と費用が重い。そこで GUI の人間は「何をしたか」だけを卓に書き、
区切りで審判にまとめて頼む。

- GUI の行動: 土地を出す（`move` だけ）、唱える（`cast`。対象と文は任意。支払いなし）、起動する（`stack_push`）、攻撃・ブロック、
  タップ・移動・カウンターなど。マナの Note、タップイン、コストの支払い、誘発、解決、状況起因処理は書かない
- 未確認の行動: 最後の審判の Batch（`ruled` を含む Batch）より後の、宣言・パス・ステップの進行・手順以外の件（`play.routine`）。
  GUI は Player の log の `judge` / `routine` / `request` で数え、審判のプロンプトは `prompt.unreviewed` で同じ件を出す
- 依頼文: 「行動: 1. … 2. …」「依頼: …（ボタンに無い操作・スタックの解決）」「その後: パス / 続ける / ターン終了」「補足: …」。
  「その後」は下書きの最後の行で決まる（進めるボタンで足す「○○へ進む」「ターン終了」「パス」。無ければ自分のターンは
  続ける・相手のターンはパス）。送るボタンは「審判に依頼（その後: ○○）」の1つで、選ぶ欄は置かない。
  GUI は送る前の文（行動・補足）を表示し、送ったら `declare intent` として卓に残る（相手にも見える。審判のプロンプト本体は全情報を
  含むので GUI には出さない）
- 審判は未確認の行動を古い順に確かめ、足りない処理を補い（judge.md の「未確認の行動を確かめる」）、ルールに合わない行動は戻す
- 審判を呼ぶのは「審判に依頼」のボタンだけ（下書きが空でパスになるときは依頼にせず、そのまま `pass`）
- 取り消し（`play.undo_refusal`）: 依頼する前の自分の行動は、新しい方から何度でも取り消せる。送った依頼・審判の処理
  （ruled を含む Batch）・引いた／見た行動（`reveals`）より前には戻らない。審判が処理している間（waiting_on が judge）は
  GUI が行動を記録しない（審判が見ている盤面を変えない）

残り: カードごとの処理表（出せるマナ・タップインの条件をデッキ単位で先に作り、GUI と審判が使う）。

## どこで止めるか

審判はステップ・ターンを、次に判断が要る所まで一度に進める（ターンの開始は既定でメイン1まで）。止めるのは、誘発・選択、
Player の「止める場所」、依頼の中の指示のとき。人間・AI とも推測では止めず、Player が「止める場所」で明示した場面だけ
（judge.md「どこで止めるか」）。それ以外の応答の機会は、人間の席も AI の席と同じく自動でパスする（`play.autopass`）。

- 止める場所は非公開: 卓の記録に載せず、`private/<席>.json` に置く（`play.get_stops` / `set_stops`）。本人と審判のプロンプトにだけ出る。
  `own:<ステップ>` / `opp:<ステップ>` と、`opp:spell`（相手が呪文・能力を積んだとき）/ `opp:attack`（相手が攻撃したとき）。
  GUI は「止める場所…」（`GET/POST /api/games/<g>/stops`。席の鍵が要る）、AI は返答の `stops`
- 止めた理由を label・message に書かない（手札の中身が伝わる）

## 公開範囲（記録の時点では非公開）

- （前の形）Player が直接記録した行動は、審判が処理するまで相手に見せない（`play.visible_cursor`。今は席が卓に書かないので外した: 最後の審判の Batch より後で、他の Player の、
  手順・宣言・パス・ステップ以外の件があれば、その手前まで）。席の view・時系列・Log・AI のプロンプトはここで止まる
- 依頼・回答・質問（`intent` / `answer` / `ask`）の中身は、本人（質問は質問された Player）と審判だけ（`info.PRIVATE_KINDS`）。
  相手の Log・プロンプトでは「（審判とのやりとり）」とだけ出る。審判の処理（`ruled` と message）と処理後の盤面は公開
- 待たれている Player とは別の Player の未確認の行動が残っていれば、AI のプロンプトより先に審判を呼ぶ（`prompt.next_role`）。
  GUI の「パス」も、未確認の行動があれば審判への依頼（その後: パス）になる

## 優先権の往復を減らす（g1 の検証から）

g1 で「パスの確認」が頻発した原因と対応:

| 原因 | 対応 |
|---|---|
| 審判が `turn_start` の `to` を書き忘れ、ドロー・ステップで止まる。人間の土地・呪文が巻き戻され「メイン1へ進みますか」と聞かれる | 審判の Batch の `turn_start` に `to` が無ければ `main1` を補う（`prompt.judge_acts`） |
| 全員がパスして優先権が空になると、待たれるのが「スタックの一番上のコントローラー」（人間）。人間が毎回「解決を依頼」する | 審判のいる対局（ruled がある）では、全員パスでスタックが残れば審判の番（`play.resolve_pending`）。審判はそのまま解決し、続くパスも判断して進める |
| 人間の呪文のたびに AI の席に優先権が回り、AI を呼んで pass を返させていた | AI の席は、止める場所に当たらない応答の機会を自動でパスする（`play.autopass` / `needs_player`。API を呼ばない）。自分のターンの空のスタック・自分の呪文が一番上・ブロックを決める所・止める場所に当たる所では AI に聞く |
| 誘発を積んだ後に、また人間にパスを求める | 審判の指示に「積んだだけで止めない。対応しうる・止める場所に当たるときだけ止める」を足した（judge.md「優先権の流れ」） |
| それでも審判が「対応しうる」と判断して人間にパスを求める（相手のアップキープの誘発など） | 人間の席も AI と同じ決まりにした: 審判の推測では止めず、止める場所に当たらない応答の機会は自動でパス（`play.autopass` / `needs_player`） |
| 止める場所（opp:spell・opp:end）に当たるたびに、土地も無い・全部タップ済みの AI に聞いてパスを返させていた（g1 で p2 の8回中5回） | 止める場所に当たっても、何もできない席には聞かない（`play.can_respond`）。アンタップ状態のパーマネント・マナ・タップ状態でも起動できるマナ不要の能力・0 マナや代替コストのインスタント／瞬速が無ければ自動でパス。オラクルの分からないカードがあれば聞く（控えめに） |
| それでも AI の席が、マナの足りない場面で `opp:spell` に当たるたびに止まり、パスを返していた（g1 の T11 で、土地が全部タップ済みなのにアンタップの <Theorist's Proxy> があるだけで8回） | 卓はカードの文を判定しない方針なので、払えるかは AI が判断する: AI の指示（player_intent.md の `stops`）に「ブラフで止めない。払えて対応するつもりの場面だけに置き、マナを使い切る・構えをやめるときはその返答で外す」を足した |

## auto の待ち合わせ（イベント）

`auto --watch` は、`serve` の更新通知（SSE `/api/games/<対局>/events`）につないで待つ（`llm.Changes`）。サーバーは自分が書いたら
（GUI の操作・取り消し・自動パス）`Viewer.notify` で SSE の購読者をすぐ起こし、別のプロセス（CLI・auto 自身）の書き込みは
0.5 秒ごとの stamp の見張りで拾う。サーバーにつながらない間は1秒ごとに卓を見て、10秒ごとにつなぎ直す。
OS のファイル変更通知は標準ライブラリに無いので使わない。API を呼ぶ処理はサーバーと別のプロセスのまま（API の不調が GUI に響かない）。
